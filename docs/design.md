# MappyWall Design Notes

MappyWall is a client-only Fabric mod for planning and opening map walls on vanilla-compatible servers.

Current implementation targets Minecraft `26.2` with its official unobfuscated names and Java 25.

## Current boundaries

- Manual routing is available and remains the safest/default mode.
- Automatic walking is available as an explicit mode. It uses vanilla-compatible client inputs, movement packets, and interactions, including sprinting, jumping, conservative local path planning, opt-in block breaking/placing, eating, and optional boat use when water is encountered.
- Elytra/firework automation is available as an explicit automatic mode, including a separately visible aggressive style.
- The core planner has no Minecraft dependencies so route math, binding recovery, and persistence can be tested without launching the game.
- Client integration must not register blocks, items, entities, server packets, or any behavior that assumes a Fabric server.

## Map wall model

The first planned map is anchored to the map region containing the player when the project is created. Wall columns move east (`+X`) and rows move south (`+Z`). The MVP route uses a snake pattern to reduce travel distance while preserving row-major wall coordinates for final hanging instructions.

Map bindings use region signatures instead of contiguous map ids. One wall cell may retain multiple equivalent ids, shown as `4/5` in the final hanging order, so duplicate maps of the same region are useful choices rather than conflicts. Empty maps always open as vanilla scale 0 maps. Vanilla's clientbound map packet does not include map-center coordinates, so automatic and manual openings bind a newly allocated id to a position-validated target; client placeholder centers must never create, move, or erase bindings.

## Server compatibility

Inventory operations are conservative and re-check client state before continuing. If an operation cannot be verified, the run pauses and the HUD tells the player what needs attention. Automatic movement is behind an explicit mode, shows an on-screen warning, and can be paused with `U` or emergency-stopped with `K`.

## Automatic walking and aggressive mode

- Route planning is local and incremental: for each target map region, the navigator aims for the nearest reachable point inside the region rather than forcing the player to stand on the map center.
- Partial routes may end only at a loaded, standable, surface-like `SAFE_FRONTIER`. Surface height, accumulated covered depth, and underground exposure are part of endpoint selection, so a horizontally closer cave or covered dead end cannot displace a safer, reversible surface continuation.
- At equal safety, a partial frontier is chosen by remaining target distance before path cost, so a cheap one-step prefix cannot displace a farther connected prefix. Reaching the ordinary search-node limit returns the best already-proven safe or unloaded progress prefix; an empty `NODE_LIMIT` is reserved for searches that found no executable progress and uses only a short retry yield.
- Drops greater than one block create unrecovered-drop debt. An incomplete route carrying that debt is rejected until the same route regains the pre-drop safe height; this prevents a sequence of locally valid segments from ratcheting the player down cliffs or into holes.
- Drop-debt search uses Pareto dominance and a bounded 384-node proof window after a cliff candidate appears. Modification-aware search runs only after an exhaustive `NO_PATH`, never merely because the ordinary node budget ended; this keeps cliff and cave detour work bounded without making breaking or placement an early shortcut.
- A covered or underground passage is executable only when the same planned segment proves a safe surface-like exit or reaches the valid navigation target. When already underground, recovery may temporarily move away from the horizontal target if that reduces covered depth or returns toward a safe altitude.
- Path searches run on a dedicated daemon thread. The client thread incrementally captures a bounded, loaded-chunk-only terrain snapshot in batches of at most 512 columns; the current 57×57 window freezes after seven batches, and only that completed immutable snapshot is submitted to the search worker.
- Path execution uses active, pending, and buffered segments. With safe steps still remaining, lookahead capture is anchored to the active segment's exact planned endpoint (the seam), allowing planning to continue while the player moves. A valid buffered continuation is promoted at the seam in the same client tick, avoiding an input-neutral pause between local segments.
- Rolling lookahead begins while as many as 28 safe steps remain and may be requested both before and after same-tick waypoint advancement. Successful planning has no fixed cooldown. Real `NO_PATH` and current worker failures use a 20-tick failure backoff, while an empty `NODE_LIMIT` yields for two ticks; stale or live-invalid results request a fresh snapshot immediately.
- Continuation policy is explicit per segment. A non-modifying safe frontier prefetches immediately, a non-modifying unloaded frontier starts as soon as the exact seam plus a four-block target-directed feet/head/support probe is in loaded chunks, and terminal or world-modifying segments do not prefetch. Readiness is checked only on the client thread; the worker remains isolated from live Minecraft state.
- A lookahead result is accepted only when its target key and generation still match, its planned start equals the requested seam, the active suffix still ends at that seam, and the seam plus the continuation's first live transitions remain loaded, adjacent, collision-free, supported, and non-hazardous. Lookahead is not performed across unresolved breaking or placement steps that could invalidate its terrain snapshot.
- Every path step is checked again against the live world before execution. Upward traversal is limited to a normal one-block jump, jumping requires ground or water contact, drops are limited to three blocks, and unloaded or hazardous cells are rejected.
- Before an asynchronous initial path is installed, its prefix is rebased and checked against the player's actual feet. Up to three already-consumed non-modifying movement steps may be trimmed, but BREAK/PLACE is never skipped; the first three remaining live transitions are rechecked for adjacency, diagonal clearance, collision, support, fluids, and hazards. A first stale-prefix rejection captures again immediately, while repeated invalid prefixes use bounded failure backoff.
- When no verified waypoint exists, normal input and vehicle controls are released as before. Aggressive mode additionally clears only the player's residual horizontal velocity while preserving vertical velocity, preventing a stale plan from pulling the player back and forth across one block during a planning gap.
- Normal mode follows camera-facing vanilla input. Aggressive mode keeps a separate server-facing travel direction so the player may free-look or keep an ordinary inventory screen open, while horizontal speed and vertical motion remain bounded.
- Block placement is a fallback with a high path cost and a strict cobblestone/dirt whitelist. In aggressive mode placement is a non-blocking side action: movement may continue cautiously while the controller waits for the server to confirm the new support block, and the accepted path is retained after confirmation.
- Placement and breaking use two phases: after the world change is acknowledged, the controller must safely enter and land in that waypoint before the movement path can advance. World and inventory interactions remain on the client thread; only immutable path search work runs in the background.
- Aggressive mode enables a conservative natural-terrain breaking whitelist by default. Players can disable breaking, edit the ids, or switch between whitelist and blacklist in the navigation settings; the configuration is persisted in `config/mappywall/navigation.json`. Breaking remains the last planning resort with a higher cost than bridging, and fluids, block entities, unbreakable blocks, and dangerous blocks are rejected independently of the user list.
- Missing paths, stale plans, placement acknowledgement failures, collisions, and stalls release movement input and use bounded retries before pausing. They never trigger blind forward movement or unconditional jumping.
- Changing to the next map region advances the target generation and immediately invalidates active, pending, buffered, capture, and search state; no old walking, jumping, breaking, or placement waypoint may run for the new target.
- Input, sprint/sneak, boat paddle, and aggressive server-look state are reset on pause, emergency stop, project/world changes, vehicle changes, and other terminal transitions.
- This navigation work does not change sprint, swimming, boat, Elytra, block-placement, block-breaking, or packet/movement speed constants.
- Target and path markers use Minecraft 26.2's level render-state API and render after translucent world features.

## Map opening, zooming, and fill verification

- Before an empty-map use is sent, the mod derives the vanilla scale-0 region from the player's current coordinates, projects it to the task scale, and durably records that region plus the exact slot where vanilla will return the filled map. Automatic opening additionally requires the position to remain stable across ticks. Only a new id arriving in that transaction slot can complete the opening; a filled map picked up elsewhere cannot impersonate it. Container mutations are briefly held while this evidence is unresolved. Pending openings survive pauses, late acknowledgements, disconnects, and restarts; after a 15-second timeout the run pauses, and an explicit resume atomically discards the stale transaction before retrying.
- Manual and creative openings use the same pre-use transaction hook. The captured position determines the route region instead of assuming it is the next missing cell, so a second map opened in an already completed region is retained as an alias such as `4/5`.
- A provisional id that later proves to belong to another task region is automatically migrated there as an alias, releasing the originally intended cell so automation can open a replacement. Only contradictory observations for one id, a previously positively verified id being invalidated, corrupt saves, or different jobs persistently assigning the same verified id to different regions enter `CONFLICT`. Cross-job conflicts list the involved job ids and can be resolved by deleting stale jobs from the task screen.
- Both open-first and fill-after-open projects require a positively verified target-scale map id before a cell can complete. This also reopens premature high-scale completions written by older saves when they are loaded.
- Fill-after-open leases the offhand for the exact target-scale task map so temporary main-hand changes for blocks, food, boats, or fireworks cannot interrupt map updates. Completion uses coverage growth/stability observations, conservative minimum coverage thresholds, and bounded repeat passes instead of treating inventory presence as completion.
- Cartography lineage is tracked for manual, normal, and aggressive workflows by intercepting the actual result-slot action rather than polling previews. Before the click is sent, the source id, owned source-copy count, expected scale, existing ids, and transaction time are persisted. The non-owned result preview is excluded from source counts. A replacement is adopted only after the owned source count decreases and one new owned id appears; its scale is inherited from the verified scale recipe, so a delayed MapState packet cannot deadlock the job. Another copy with the same source id no longer blocks acknowledgement. Only an empty-cursor left click or a Shift+left click with output space is tracked; clone, throw, swap, drag, and other ambiguous result actions are blocked for task maps. Locally non-consuming clicks roll back immediately, unresolved server actions pause after 15 seconds, and resume provides an explicit retry path.
- When several lineage-related copies exist, automatic cartography always chooses the highest known scale first. A lower-scale source stack left in the input is returned before the newly scaled output is inserted, so clones are not repeatedly scaled while the actual output is ignored.
- Inventory observations include main inventory and offhand, deduplicate map ids, and cache scale/coverage metadata within a tick. Region reconciliation is performed only for observations whose center is actually known; ordinary vanilla client placeholders are matched through persisted map-id lineage instead.
- Saves written before position-validated lineage was introduced are marked by a binding-data revision. On first load, all potentially placeholder-derived bindings are demoted to provisional aliases and their route cells are reopened from validated positions instead of being silently trusted.
- Saves are written through a same-directory durable temporary file with atomic replacement when supported. A validated backup is used only to recover a present but corrupt primary file; deleting a project cannot resurrect its backup.
